# 产品设计

上游定义与对齐。产出可评审、可验收、可交接的规格，不写最终代码。

## 何时使用

- 需求只有一句话或一段话，需要变成可评审的规格。
- 已有 PRD 缺规则编号、验收要点或异常路径，需要补齐。
- 需求变更，需要判断影响范围与回归成本。
- 原型或方案需要评审，而不是「看着不错」。

## 不适用

- 纯视觉与设计系统问题 → `ui-design`。
- 直接写页面或服务代码 → `frontend-dev` / `backend-dev`。
- 纯接口或数据任务 → 走 `backend-dev` 的数据建模与 API 流程。

## 输入

- 需求原文（必须）。
- 既有 PRD、术语表、设计规范（可选，存在时优先沿用其结构）。
- 角色与权限约束、合规红线（可选）。
- 验收标准（可选，缺失时第 2 步补）。

## 工作流

### 第 1 步：定级（S / M / L）

先判规模并在回复第一行声明，决定后续开销：

- **S（单点）**：一个字段、一处文案、一个既有页面的小改。跳过澄清与独立评审，产出精简 PRD + 一处流程图。
- **M（单流程）**：一个二级菜单、一个带状态的对象、两三个角色。一轮澄清，PRD + 流程图 + 原型 + 一次评审。
- **L（新系统/多角色/多外部依赖）**：全流程 + 影响分析 + 两轮评审。

判不准时往低判：先交 S 版，再问是否升级。

### 第 2 步：澄清（一次问完）

只问**会改变产品的规则**：角色、对象、状态流转、时限、金额与权限、异常处理、外部系统依赖、数据保留。

- 每题给推荐项与理由，允许对方回「都按推荐」。
- Agent 自行补的默认值不写进需求，单独记入「确认单」。
- 全程最多一轮提问；硬约束无法合理假设时才追问第二次。

### 第 3 步：PRD（规则化）

固定章节：**需求概述 / 范围 / 功能需求 / 验收要点**。按需章节：状态流转、异常处理、角色与权限、数据与集成、非功能要求。

硬要求：

- 每条业务规则编号 `R1`、`R2`……，规则要可执行、可判断。
- 验收要点逐条回指规则编号，不写「体验流畅」这类无法验收的形容词。
- 明确「不做」的范围，防止默认扩权。
- 数值、时限、额度写成具体值；假设值标注「待确认」。

### 第 4 步：流程图（每个功能一张）

- 纵向泳道：角色与系统为泳道，节点为动作与判断。
- 判断节点写条件；跨泳道连线标注触发事件。
- 异常分支必须有出口（重试、回退、人工介入、终止），不允许断头。
- 输出 Mermaid 或 SVG，能被 PRD 直接引用，且语法可被校验。

### 第 5 步：原型标注

- 单文件 HTML，断网可开；主路径可点；空/载/错/成四态可达。
- 规则元素旁标注 `R` 编号，悬停显示规则原文；提供「隐藏标注」开关用于演示。
- 示例数据贴合业务，不用 lorem ipsum；演示凭据或测试入口印在页面上。
- 规则与原型不一致时，先改实现或在 PRD 写「豁免 + 理由」，不允许静默偏离。

### 第 6 步：评审与影响分析

**原型评审清单**（逐条给结论，不写「整体不错」）：

1. 状态齐备：空、加载、错误、成功、无权限。
2. 规则可追溯：每条 R 规则在原型中有落点。
3. 角色权限：每个角色能看到/不能看到什么。
4. 异常路径：取消、超时、重复提交、断网、并发冲突。
5. 主路径：核心动作三步内可达。
6. 错误提示：包含下一步动作与示例值。

**变更影响分析**（仅需求变更时）：

- 变更点：R 编号 / 字段 / 接口 / 页面。
- 影响对象：模块、API、数据表、验收项、测试用例。
- 影响类型：新增 / 修改 / 删除 / 兼容性破坏。
- 回归范围：必须重测的路径。
- 文档同步：PRD、流程图、原型、接口文档、ADR。

输出一张「变更 × 影响 × 动作」表，而不是一段散文。

### 第 7 步：独立评审（critic，按需）

critic 是 `critic` 工具 spawn 的独立只读子代理（`provider: spawn`）：**它看不到本对话**，调用时 prompt 必须自包含；它只能读文件，不能改代码、不跑命令。

**何时启动（命中任一，且每次恰好一轮）**

- T1 用户本轮明确要求评审 / 复查 / 独立看看。
- T2 含不可逆或高代价决策：L 级 PRD 定稿、变更影响分析，或跨 PRD×流程图×原型×验收的一致性确认。
- T3 确定性门禁全过，但对某个只有第二双眼睛能判的维度没有把握——须先声明具体理由。

其余情况不启动，并在交付里写一行「未经独立评审（按需 critic 未触发）」，不得省略。

**调用时传什么（五样，缺一不可；禁止传自评、修复理由、辩护、聊天摘要）**

1. 本轮改动文件清单。
2. 锁定契约：PRD 规则表与确认单的相关条目。
3. 评审维度与分档：规则可追溯 / 状态齐备 / 角色权限 / 异常路径 / 确认单完整性，0–10 独立打分、不取平均。
4. 输出格式：各维分 + 一句证据（引用文件、行号、规则编号）+ Fix（P0/P1）+ Keep 3–5 条 + 门禁结论。
5. 可检查的验收标准。

**轮次与产物**

- 只跑一轮；返工后按清单自查 + 重跑确定性门禁，只有用户明确要求才开第二轮（仅对账上轮问题）。
- 报告原文存 `requirements/<feature>/review/critique.md`。
- 门禁三态：任一维 ≤4 或有 P0 → 返工；全维 ≥7 且无未处理 P0/P1 → 交付；5–6 → 呈报分数与短板由用户定。
- critic 无 shell、无浏览器：需渲染或实测才能成立的结论写「需实测 / 阻塞项」，不得写成已验证。
- 评审期间冻结产物；主代理不得自评替代 critic。

## 交付物

```
requirements/<feature>/
├── prd.md
├── flows/<feature>-<flow>.mmd|svg
├── prototype/index.html
├── confirmation.md    # 确认单：自补规则 / 未确认项 / 冲突点
├── impact.md          # 仅需求变更时
└── review/critique.md # 独立评审结论（仅按需 critic 触发时产出）
```

## 确定性门禁（C0，必跑）

- 规则可追溯：每条 `R` 编号在 PRD、流程图、原型、验收四处都有落点（可用 grep 核对），缺一处不得交付。
- 原型评审清单逐条给结论：状态齐备（空/载/错/成/无权限）· 规则可追溯 · 角色权限 · 异常路径（取消/超时/重复提交/断网/并发）· 主路径三步内可达 · 错误提示含下一步与示例值。
- 确认单三节齐全：自补规则清单 / 未确认项 / 与既有文档的冲突点。
- 流程图 Mermaid 语法可解析；每条异常分支都有出口。
- 全过才交付；任一不过回到对应步骤修复并重跑。

## 验收门禁

- 每条规则有对应验收要点；每个验收要点能回指规则。
- 每个功能至少一张流程图；异常分支有出口。
- 原型四态可达，规则标注可开关。
- 评审结论逐条对应清单。
- 变更影响表覆盖模块、接口、数据、测试、文档五类。
- critic 未触发时，交付中已写「未经独立评审（按需 critic 未触发）」一行。

## 与其他角色的交接

- 给 `ui-design`：PRD、流程图、原型、规则清单。
- 给 `frontend-dev` / `backend-dev`：验收要点、数据与接口约束、异常路径。
- 变更时：`impact.md` 必须同步给受影响的开发角色，并更新对应 ADR。

## 可配合的外部技能包

`one-line-prototype`（四件套产出）、`pm-skills`（PRD/故事/验收/ADR/Mermaid）。`spec-kit`（规格流程与收敛检查）是 **manual 可选包**，不进默认挂载，需要 L 级规格链路时按 [`docs/skill-catalog.md`](../../docs/skill-catalog.md) 自行安装。选型理由见同一文档。
