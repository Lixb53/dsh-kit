# 后端开发

不追求「生成最多代码」，追求**在正确约束下给出有依据的方案**。每条建议都要能回答：为什么是它、代价是什么、什么情况下不适用。

## 何时使用

- 需要做架构决策（单体/微服务、同步/异步、选型）。
- 需要数据建模、API 契约、迁移方案。
- 需要可靠性设计（超时、重试、幂等、熔断、降级）。
- 需要数据库操作、索引与容量评估。

## 不适用

- 纯前端交互 → `frontend-dev`。
- 需求规则未定 → `product-design`。

## 输入

- 业务约束：QPS、数据量、增长预期、一致性要求、SLA。
- 现有栈：语言、框架、数据库、消息、缓存、部署环境。
- 团队约束：人数、运维能力、合规要求、预算。

## 工作流

### 第 1 步：先写约束，再写方案

在给任何方案前，列出：

- 规模：峰值 QPS、日增数据量、读放大倍数。
- 一致性：强一致 / 最终一致 / 允许丢失窗口。
- 延迟预算：P99 目标，拆到每个调用。
- 可用性：可接受停机与降级形态。
- 团队：能维护多少组件、是否有 SRE。

约束缺失时先问或显式假设，并把假设写进 ADR；不要用「视情况而定」跳过。

### 第 2 步：架构决策记录（ADR）

每个非平凡决策写一篇，Nygard 格式：

```
# 0007. 用 Outbox 代替双写

## 状态
Accepted

## 背景
订单写入后要发消息，双写存在不一致窗口……

## 决策
订单表同事务写 outbox 表，由投递器异步发送。

## 备选
- 双写：简单但会丢消息
- CDC：无需改业务，但引入 Debian 依赖与延迟

## 后果
+ 不丢消息；- 多一张表与一个投递器；需处理重复投递
```

决策要可被反驳：写清「什么情况下应推翻它」。

### 第 3 步：数据建模

- 先定实体、关系、不变量，再定表结构。
- 主键策略、索引、唯一约束、外键与级联行为显式写出。
- 状态字段用枚举 + 状态机，禁止散落的布尔组合。
- 软删除、多租户、审计字段在建模阶段定，不后补。
- 迁移必须可回滚或有前滚方案；大表变更说明锁与耗时。

### 第 4 步：API 设计

- 资源与动作语义清晰；命名一致；错误码可被客户端分支处理。
- 分页、过滤、排序、幂等键、限流、版本策略显式定义。
- 请求/响应示例与错误示例都要给，不只给 happy path。
- 契约变更走兼容策略（新增字段优先，删除走弃用期）。

### 第 5 步：可靠性与数据操作

- 超时、重试（仅幂等调用）、退避 + 抖动、重试预算。
- 幂等键、去重表、Outbox/Inbox、补偿（Saga）按需组合。
- 缓存：失效策略、穿透/击穿/雪崩防护、一致性边界。
- 数据库：连接池、慢查询、索引验证（EXPLAIN）、锁与事务边界。
- 可观测性：关键指标、日志字段、追踪埋点，先于上线。

### 第 6 步：容量与失败模式

- 背 envelope 计算：QPS × 大小 × 副本 → 带宽/存储/连接数。
- 列出失败模式与应对：依赖超时、消息积压、主从延迟、热点键、雪崩。
- 给出降级顺序与不可用时的用户可见行为。

## 验收门禁

- 每条建议有依据（规则/基准/实测），不凭印象。
- ADR 含背景、决策、备选、后果与推翻条件。
- 数据模型含不变量、索引、迁移与回滚。
- API 含错误码、幂等、分页与版本策略。
- 可靠性设计含超时/重试/幂等/降级的具体值，不写「做好重试」。
- 数据库操作默认只读；写操作有审批与回滚路径。

## 与其他角色的交接

- 从 `product-design` 接：验收要点、数据约束、异常路径。
- 给 `frontend-dev`：OpenAPI 契约、错误码、分页/缓存语义。
- 变更时：更新 ADR 与 `impact.md`，标注兼容性破坏。
