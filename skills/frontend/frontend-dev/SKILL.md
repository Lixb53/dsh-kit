# 前端开发

不追求「生成最多代码」，追求**在正确约束下交付可维护的实现**。

## 何时使用

- 有设计稿、方向卡或交互方案，需要落地为代码。
- 需要新增页面、组件、状态管理或数据获取逻辑。
- 需要做性能优化、E2E 测试或前端代码审查。
- 需要把设计令牌接进现有工程。

## 不适用

- 视觉方向还没定 → 先走 `ui-design`。
- 需求规则还不清楚 → 先走 `product-design`。
- 服务端架构与数据建模 → `backend-dev`。

## 输入

- 设计产物：方向卡、令牌、组件规范、原型。
- 工程现状：框架与版本、路由、状态管理、样式方案、测试框架。
- 验收标准：性能预算、浏览器范围、可访问性等级。

## 工作流

### 第 1 步：读工程，再动手

先回答四个问题，再写第一行代码：

1. 框架与版本（React 19 / Next 15 / Vue 3 / Nuxt / Svelte）？
2. 样式方案（Tailwind v4 / CSS Modules / CSS-in-JS）与令牌从哪里来？
3. 数据获取方式（RSC、TanStack Query、SWR、服务端 API）？
4. 既有测试与 CI 命令是什么？

不发明第二套设计系统；不引入与现有依赖冲突的新库。

### 第 2 步：组件

- 组件 API 先定：props 语义化，避免布尔 prop 泛滥；多变体用显式变体或复合组件。
- 状态就近：能局部不全局；跨层用 context 或组合，不靠 prop drilling。
- 受控/非受控行为明确；表单错误与禁用状态可被外部驱动。
- 可访问性内建：语义标签、label 关联、focus 可见、键盘可达、`aria-live` 用于异步结果。
- 组件必须能独立渲染（Storybook/测试页均可），不依赖页面级副作用。

### 第 3 步：性能

按影响排序处理，不做过早微优化：

1. 消除请求瀑布（并行取数、预取、避免串行 await）。
2. 包体（动态导入、避免 barrel 导入、按路由拆分）。
3. 服务端性能（缓存、流式渲染、避免重复序列化）。
4. 客户端取数（去重、缓存、乐观更新）。
5. 重渲染（状态下沉、memo 只用在验证过的热点）。
6. 渲染与 JS 微优化（长列表虚拟化、避免布局抖动）。

预算（可按项目调整，但必须显式写进验收）：JS < 300KB gzip、CSS < 100KB gzip、首屏图片 < 500KB、LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1。

### 第 4 步：测试

- 单元/组件：覆盖状态分支与边界，不测实现细节。
- E2E：只覆盖核心用户路径（登录、主流程、支付/提交、错误恢复），用角色与可访问名称定位，不用脆弱的 CSS 选择器。
- 每个 E2E 用例能独立运行、可重试、失败有截图/trace。
- 交付前在真实浏览器跑一遍，不以「代码看起来对」代替运行结果。

### 第 5 步：审查

输出格式固定，便于执行：

```
[blocking] src/components/Button.tsx:42 — 事件处理未防重复提交，连点会发两次请求
[important] src/pages/List.tsx:88 — 列表未虚拟化，1000 条时首屏渲染 2.3s
[nit] src/lib/format.ts:12 — 建议命名 formatCurrency
```

- 每条给文件:行号、问题、影响、建议；不给「建议优化」这类空话。
- 区分 blocking / important / nit / praise。
- 审查范围：逻辑正确性、边界、安全（XSS/注入）、性能、可测试性、可访问性；格式问题交给 linter。

### 第 6 步：独立评审（critic，按需）

critic 是 `critic` 工具 spawn 的独立只读子代理（`provider: spawn`）：**它看不到本对话**，调用时 prompt 必须自包含；它只能读文件，不能改代码、不跑命令、不跑浏览器。

**何时启动（命中任一，且每次恰好一轮）**

- T1 用户本轮明确要求评审 / 复查 / 独立看看。
- T2 含不可逆或高代价决策：大重构、性能预算敏感改动、架构或技术选型取舍。
- T3 确定性门禁全过，但对某个只有第二双眼睛能判的维度没有把握——须先声明具体理由。

其余情况不启动，并在交付里写一行「未经独立评审（按需 critic 未触发）」，不得省略。

**调用时传什么（五样，缺一不可；禁止传自评、修复理由、辩护、聊天摘要）**

1. 本轮 diff 涉及的文件清单。
2. 锁定契约：方向卡与令牌的相关条目。
3. 评审维度与分档：正确性 / 性能 / 安全 / 可维护性，按严重度输出。
4. 输出格式：`[blocking]/[important]/[nit]/[praise] 文件:行号 — 问题 — 影响 — 建议` + 门禁结论。
5. 可检查的验收标准（性能预算、浏览器范围、可访问性等级）。

**轮次与产物**

- 只跑一轮；返工后按清单自查 + 重跑确定性门禁，只有用户明确要求才开第二轮（仅对账上轮问题）。
- 报告原文存 `app/review/code-review.md`。
- 门禁三态：存在 P0 或被判不通过 → 返工；全维通过且无未处理 P0/P1 → 交付；其余呈报用户。
- 禁止全量代码库扫描，只看传入的 diff 范围；评审期间冻结产物。
- critic 无 shell、无浏览器：需实测的结论写「需实测 / 阻塞项」，不得写成已验证。
- 主代理不得自评替代 critic。

## 交付物

```
app/
├── src/
├── tests/
│   ├── unit/
│   └── e2e/
├── perf-report.md          # 预算与实际测量（有性能改动时）
└── review/code-review.md   # 独立评审结论（仅按需 critic 触发时产出）
```

## 确定性门禁（C0，必跑）

- 修改后必跑：类型检查、lint、构建、相关单测；命令以项目 `package.json` scripts 为准，不猜命令。
- E2E 核心路径真跑；未真跑不得写「已验证」。
- 性能结论必须有测量数据（Lighthouse / CWV / DevTools trace 或项目内脚本）；预算不达标需显式豁免与理由。
- 审查意见必须带 `文件:行号` 与严重度；无证据的空泛建议删除。
- 控制台无报错、无未处理 Promise rejection。
- 全过才交付；任一不过回到对应阶段修复并重跑。

## 验收门禁

- 主路径可运行、可点击、四态可达。
- 控制台无报错；无未处理的 Promise rejection。
- 性能预算达标或有显式豁免与理由。
- E2E 核心路径通过；失败用例有诊断信息。
- 无硬编码颜色/间距（令牌外）；无 Emoji 结构图标。
- 审查结论逐条带文件:行号。
- critic 未触发时，交付中已写「未经独立评审（按需 critic 未触发）」一行。

## 与其他角色的交接

- 从 `ui-design` 接：方向卡、令牌、组件规范、原型。
- 给 `backend-dev`：接口契约、错误码、需要服务端配合的分页/缓存策略。
- 接口未定时：先按契约写 mock，不把假设埋进组件。
